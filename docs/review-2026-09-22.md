# Design-tool evidence review — 2026-09-22

## Decision

Keep the ALGAL execution and provenance infrastructure. Redirect the main
experiment toward patterns that construct working code and support later
changes. Pause expansion of text-format and partition tournaments as evidence
for code-design usefulness. The original thesis is plausible and testable;
the current results do not establish it.

A useful pattern should tell an agent **when a relationship is appropriate,
which conflicting demands it resolves, how to construct it, what it costs,
and when to use something else**. An executable wrapper around an explanation
is not enough. A library of such patterns should help produce and adapt a
coherent whole, rather than merely supply names for pieces.

This interpretation is consistent with Alexander's own question about whether
a system of patterns generates coherent programs in his
[OOPSLA address](https://www.patternlanguage.com/archive/ieee.html). His
[account of sequences](https://www.patternlanguage.com/patterns/justsostory.html)
emphasizes ordered decisions adapted to context. Our machine-checkable code
experiment tests a narrow engineering claim; it does not operationalize his
entire account of human experience or architectural quality.

## What the results actually establish

1. **Execution and accountability work.** Manifests, bounded calls, digest
   composition, fixtures and receipts make a design procedure inspectable.
   Mechanical contracts can stop a model-preferred invalid candidate from
   inheriting a slot. These capabilities are worth preserving.
2. **The synthesis artifact is text.** `programs/diagram.algal.json` asks for
   a one-cell constant text manifest; `programs/realize.algal.json` joins the
   fragments. Successful execution does not show that the procedure generates
   useful low-level code or composes software responsibilities.
3. **Clustering has a modest historical signal and weak measured transfer.**
   The revised metric audit below changes the interpretation substantially.
4. **Coverage repair is demonstrated.** In the latest stored village run,
   `ritual-production` omitted three IDs and `settlement-ecology` omitted two;
   repair restored coverage. `subsistence-service` was complete before repair
   and became champion. Generation two contains only the incumbent and zero
   duels. This is not evidence of structural superiority over Alexander's
   solution or a defense against new alternatives.
5. **Judges produce preferences.** Different model rubrics expose disagreements,
   but agreement between them is not independent ground truth. The historical
   files labeled as human picks have unverified human provenance and are now
   explicitly excluded from validation.

## Evaluation defects and corrections

### Partition agreement was too easy to score highly

The old metric is the unadjusted Rand index: the fraction of pairs on which
two partitions agree about togetherness or separation. Most pairs are separate,
so unrelated partitions can score highly. Singletons are a diagnostic control,
not a contract-valid habitat candidate.

Reproduction, Python 3, fixed seed 0 and 200 size-preserving shuffles:

| Dataset / average linkage | Raw Rand | ARI | Shuffled ARI 95th percentile | Interpretation |
|---|---:|---:|---:|---|
| Village, 4 groups | 0.7073 | 0.2871 | 0.0196 | Association above this fixed-size null |
| Village, 12 groups | 0.8402 | 0.1716 | 0.0183 | Association above this fixed-size null; far from identity |
| ALGAL source, 10 groups | 0.7598 | 0.0414 | 0.0485 | Does not exceed this null's 95th percentile |

Singleton raw scores are 0.7480, 0.9119 and 0.9007 respectively. ARI corrects
for chance agreement conditional on group sizes; it measures similarity, not
the quality of either design. The shuffles preserve output group sizes and
coverage, but do not enforce the habitat's cohesion constraint. They diagnose
clustering association, not the whole habitat's constrained search problem.
The algorithms were already examined on these datasets: these are retrospective
diagnostics, not confirmatory significance tests or fresh holdouts.

```sh
python3 scripts/decompose-village.py 4 avg --json --baseline-samples 200 --seed 0
python3 scripts/decompose-village.py 12 avg --json --baseline-samples 200 --seed 0
python3 scripts/decompose-village.py 10 avg \
  ensembles/algal-src.ensemble.json ensembles/algal-src.decomposition.json --json --baseline-samples 200 --seed 0
```

The metric now rejects duplicate membership and unequal item universes,
reports pair counts and adjusted scores, and includes deterministic shuffled
baselines. The village gate uses the adjusted comparison in addition to the
historical regression threshold. Source transfer remains report-only. The
Python and manifest implementations share a linkage criterion but differ in
tie ordering; their exact partitions must not be assumed identical. A direct
comparison on four IDs `a,b,c,d`, no links and `k=2` gives `{a,b}/{c,d}`
in Python versus `{a,b,c}/{d}` in the manifest. The historical benchmark
therefore describes the Python algorithm, not a proven scale-up of its manifest.

### The legacy holdout and reference were visible during search

`scripts/evolve-jury.py` selects a case labeled `holdout` as the optimization
arena and feeds its standings into each subsequent writer call. In the three
partition habitats, train/validation/holdout also repeat identical arguments.
Removing the `job.oracle` key does not isolate the answer: the writer receives
a reference-derived incumbent and standings annotated with `oracleAgreement`.
The source descriptions and reference grouping also share architectural docs
as an input source.

Therefore the claim that `oracle-aligned` independently reconstructed an unseen
architecture is withdrawn. Existing receipts are retained as historical
mechanism evidence. The legacy driver remains a demo, not a generalization
harness. Renaming its splits would not repair the old experiment.

### Provenance and claims need separate treatment

A receipt can establish what ran and what a judge returned. It cannot establish
that a scoring rule captures useful design, that a reference is optimal, or
that a model improved on Alexander. The revised history removes those
inferences and distinguishes the earlier village run from the latest file.
The raw historical human-labeled files retain their data with an explicit
exclusion annotation; no human-calibration claim is made.

## The experiment that should drive the project

The [code-design pilot](../benchmarks/code-design/README.md) makes the artifact
ordinary executable JavaScript: a bounded asynchronous mapper, then a
cancellation extension. It has interacting forces that resemble a small design
problem: throughput versus capacity, concurrency versus stable ordering,
prompt failure reporting versus draining owned work, and local cancellation
versus preserving unaffected behavior.

Compare three treatments with the same requirements and model budget:

| Arm | Guidance | Question answered |
|---|---|---|
| Direct | Task specification and ordinary implementation guidance | What does ordinary code generation achieve? |
| Checklist | Explicit engineering checks | Does general extra design attention suffice? |
| Pattern sequence | Context, forces, relationships, tradeoffs and ordered transformations | Does this pattern representation add value beyond the checklist? |

Freeze the tasks, evaluator and treatment text before generation. The generator
must not read evaluator code, reference implementations, test outcomes or the
later change during its base attempt. Then provide only its original artifact,
the new request, and the same arm's guidance. Evaluate frozen candidates once;
keep unsuccessful outputs. The pilot's public evaluator is withheld from
individual generator contexts, not a secret benchmark resistant to training
contamination.

The evaluator checks observable ordering, actual concurrency, exactly-once
work, admission after failure, drain behavior and cancellation. Deliberately
broken candidates test whether those checks discriminate. No score rewards
pattern vocabulary, number of functions, architecture resemblance or judge
preference. Full contract pass rate and regressions after change are primary;
latency, cost and patch size are descriptive. Small samples characterize the
harness and failure modes, not general pattern effectiveness.

For a subsequent study, use at least three paired repetitions per arm and
multiple independently specified task families. Balance execution order and
include pattern countercontexts (for example, trivial serial processing where
coordination machinery is overhead). Split by task family, not just random
inputs. Reserve final acceptance scenarios before tuning. If all arms pass,
report a ceiling effect and choose a new task prospectively; do not invent a
post-hoc score that rewards the desired architecture.

## First actual-code smoke result

The [frozen evidence bundle](../benchmarks/code-design/results/2026-09-22-haiku-smoke/run.json)
contains the exact prompts, six generated modules, source hashes, original runner,
model usage, and expected per-case outcomes. The
[evaluation report](../benchmarks/code-design/results/2026-09-22-haiku-smoke/evaluation.json)
records the observed results. All base and change generation finished before any
candidate was evaluated; no test feedback or reference implementation entered a
generator context. Independent source inspection preceded execution.

| Guidance | Base checks | Change checks, including base regression | Complete contract: base / changed |
|---|---:|---:|---|
| Direct | 10/12 | 18/20 | fail / fail |
| Checklist | 11/12 | 20/20 | fail / pass |
| Pattern sequence | 11/12 | 20/20 | fail / pass |

Six tool-free `claude-haiku-4-5` calls reported **$0.379231** total. The provider
returned that model name, without an immutable dated revision or sampling seed.
This was one attempt per arm and stage, with the same $0.50 call cap and
240-second timeout. The frozen protocol explicitly records differences from the
larger planned pilot, including fixed arm order and no provider-enforced token
caps. It is not the six-replicate study; test cases are not independent trials.

**No pattern-specific advantage was observed.** Checklist and pattern treatments
have identical success outcomes in this single comparison. Both changed versions
satisfy the tested contract; the direct version still fails two base cases.
This is insufficient to attribute an advantage causally or generalize across
models or tasks.

All initial implementations use `null` as a no-failure sentinel, although `null`
is a permitted failure value. The direct versions also mishandle a thenable that
resolves twice. Those are concrete design failures, not judge preferences.
The next candidate pattern should make lifecycle state explicit: distinguish
running/failed state from the arbitrary failure payload, preserve the first
terminal transition, and use standard promise assimilation for arbitrary
thenables. The reference and adversarial cases supply counterexamples. Such a
revision must be evaluated under a new frozen protocol, with matched checklist
information; editing the current pattern and presenting a rerun as untouched
evidence would repeat the earlier methodology problem.

## Revisions and next steps, in order

1. **Repair the evidence foundation.** Preserve historical data, correct claims,
   strengthen partition metrics, and add an actual code evaluator. This change
   supplies that foundation.
2. **Extend the completed smoke test into a controlled pilot.** The six-call
   smoke test above gives concrete failure modes and no pattern-specific win.
   Freeze the state/lifecycle revision and matched controls before further calls;
   record every attempt, budget and evaluation. A single task is not a general result.
3. **Test transfer and adaptation.** Add a retrying I/O adapter and an atomic
   batch-update component. Use independent reference models, fault injection,
   and invariants such as no duplicate effects, no partial commit and bounded
   retries. Reuse the same pattern relationships without task-specific answer
   fragments. Test countercontexts and report added complexity.
4. **Connect validated construction to ALGAL.** Make code, design decisions,
   applied pattern versions and verifier results explicit outputs. Use the
   existing receipt/budget machinery around the experiment. Do not silently
   redefine the old prose generator as a code generator.
5. **Expand to system design only with an executable model.** A proposal for
   queues, idempotency or replication must specify a runnable simulator or
   bounded model, failure assumptions and invariants. Measure lost/duplicate
   effects, queue bounds, latency or recovery under those assumptions. A diagram
   that looks sensible is not sufficient evidence.

| Further domain | Machine-operated artifact | Meaningful checks | What remains outside the claim |
|---|---|---|---|
| Query planning / indexing | SQL and index choices on fixed workloads | Result equivalence, plan cost, storage, update cost | Business value of the workload |
| Compiler transformations | AST-to-AST passes | Differential execution, type checks, semantics on bounded inputs | Unbounded semantic equivalence unless formally proved |
| Data migrations | Forward/recovery operations on generated datasets | Preservation, round trips, concurrent-write invariants | Unmodeled production conditions |
| Constrained layout | Layout program | Non-overlap, reachability, contrast, overflow, resize invariants | Human ease of use and aesthetic quality |
| Small protocols | State machine / simulator | Safety under enumerated schedules, bounded liveness, resource use | Real-world failures outside the modeled envelope |

The preferred next investment is several transferable low-level code patterns
with evidence of both benefit and failure, followed by small system models.
A larger pattern catalog or more model juries should wait for that evidence.
